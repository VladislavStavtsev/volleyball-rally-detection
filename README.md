# Определение розыгрышей в видео волейбола

По записи матча (≈21 мин, 38 тыс. кадров, неподвижная камера) автоматически находит начало и конец
каждого розыгрыша и сторону подачи.

Это постобработка поверх готовых моделей: трекер мяча VballNetV4c (ONNX) и YOLO для игроков и мяча.
**Модели я не обучал.** Моя часть: алгоритм сегментации, ручная разметка, метрики, подбор параметров
с проверкой на отложенной половине матча, определение стороны подачи, экспорт результата.

## Результаты

Метрики по 44 размеченным вручную розыгрышам (совпадение интервалов по IoU ≥ 0.5):

| Шаг | Precision | Recall | F1 |
|---|---|---|---|
| длина + склейка + фильтр по сетке | 0.44 | 0.61 | 0.51 |
| + разрез по низкой фазе, конец на отскоке | 0.49 | 0.82 | 0.61 |
| + подбор параметров (grid search) | 0.72 | 0.82 | 0.77 |
| + сдвиг конца −1 с, min_len = 3 с | 0.93 | 0.86 | 0.89 |

- **Честная оценка: F1 = 0.85.** Параметры подбирались на первой половине матча (до 638 с),
  результат измерен на второй. F1 = 0.89 посчитан на всей разметке, параметры выбраны уже
  с её учётом.
- На каждой половине около 22 розыгрышей, поэтому один промах меняет F1 примерно на 0.04.
  Различия меньше этого значения я считаю шумом.
- Систематическая ошибка конца розыгрыша (+1.01 с) устранена сдвигом: после него 0.03 с.
- Сторона подачи определена верно в 35 из 35 розыгрышей (по «правилу трёх» точность не ниже ≈91%).

## Как это работает

Трекер мяча даёт по каждому кадру `Visibility`, `X`, `Y`. Дальше:

1. `remove_jumps`: убирает одиночные выбросы детектора (скачок мяча дальше 150 px).
2. `fill_gaps`: заполняет короткие пропуски мяча (до 10 кадров).
3. `find_segments`, `merge_segments`: непрерывные отрезки, близкие отрезки склеиваются.
4. `filter_below_net`: оставляет только отрезки, где мяч хотя бы раз поднимался выше сетки
   (убирает касания ногой и передачи под сеткой).
5. `split_on_low_ball`: режет трек «розыгрыш + пауза + передача» по долгой фазе, когда мяч низко;
   конец розыгрыша ищется по касанию пола (`find_bounce`).
6. `filter_short`: выкидывает короткие обрывки (передачи навесом, пойманный мяч).
7. Сдвиг конца на 1 с: компенсирует систематическое запаздывание.
8. `serve_side`: сторона подачи по первой видимой точке трека (мяч у ближней стороны влетает
   с правого края кадра).

Порядок шагов важен: например, фильтр по длине должен идти после разреза, а сдвиг конца после
фильтра по длине.

## Что не получилось

- Признак скорости мяча в пикселях не разделяет настоящие розыгрыши и ложные (перспектива, скачки детектора).
- Простое «обрезать конец по последнему разу выше сетки» не помогло: передача навесом тоже идёт выше сетки.
- Короткие розыгрыши около 1 с (подача в сетку, эйс) теряются из-за порога длины: 4 розыгрыша
  потеряны ради ≈24 убранных ложных срабатываний.
- Заступ не найден, мяч, брошенный болельщиком, даёт ложный трек.

## Ограничения

- Пороги привязаны к неподвижной камере (линия сетки, граница стороны подачи). Для другой
  съёмки нужна калибровка.
- Разметка небольшая (44 розыгрыша), метрики лучше считать как ориентир, а не как точную оценку.

## Структура репозитория

```
src/
  segment.py    сегментация розыгрышей (основной алгоритм)
  evaluate.py   IoU, сопоставление, метрики, ошибки границ
  sweep.py      перебор параметров, проверка на второй половине матча
  serve.py      определение стороны подачи
  export.py     выгрузка результата в rallies.json
  explore_speed.py  эксперимент с признаком скорости (отрицательный результат)
labels/labels.csv  ручная разметка (44 розыгрыша, секунды)
app/               модели БД (SQLAlchemy 2.0)
alembic/           миграции
docs/              ER-диаграмма и схема БД
notes.md           журнал экспериментов и разбор функций
```

## Данные

Видео матча и веса моделей в репозиторий **не входят**. Разметка лежит в `labels/labels.csv`
(колонки: `number, start, end, serve_side, comment`, время в секундах).

Формат выхода трекера (`ball.csv`): `Frame, Visibility, X, Y, Radius`. Ось Y направлена вниз,
`X = Y = -1`, если мяч не найден.

## Запуск

```powershell

.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
```

Для воспроизведения нужны видео и CSV от трекера (см. раздел «Данные»). Параметры скриптов:

```powershell
python src/export.py --help
python -m src.evaluate
python -m src.sweep
```

## База данных

Схема спроектирована отдельно (таблицы `users`, `videos`, `processing_jobs`, `rallies`): см.
`docs/er-diagram.png` и `docs/schema.dbml`. Миграции создаются через Alembic (SQLite).
Сам пайплайн в базу не пишет, результат экспортируется в `rallies.json`. Детекции по кадрам лежат
в CSV, в базе предполагалось хранить только путь к файлу.

Python, NumPy, pandas, SQLAlchemy 2.0, Alembic, SQLite. Использованы готовые модели через
